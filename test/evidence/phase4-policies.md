## 一、最终定稿（一句话）

默认策略 = **`blended`（loadRatio + failRate 合成分）**，配合 **两段有界等待**、**last-resort 一次**、
**非 429 瞬时失败的二次尝试一次**、**429 冷却（rateCoolUntil）永不被重试放宽（4s 起指数退避）**，
billing 硬过滤 / pinned / 降级链语义不变。

| 关键常数 | 取值 | 说明 |
|---|---|---|
| `ADMISSION_WEIGHTS` | `{ load: 1, failRate: 1 }` | 两者同为「这次发送白打概率」的等价量纲，写死可审计 |
| `RATE_LIMIT_COOLDOWN_MS` | **4 000** | 429 是**请求级限流窗口**；15s（并发窗口）会把免费池整段踢出（扫参见 §四） |
| 有界等待 | 1200ms × ≤2 段（≤2.4s） | 第二段仅限「零上游发送 + 全部候选本地判忙」 |
| last-resort | 每请求 ≤1 次，不等待 | 瞬时类失败后按 `candidateScore` 补一次；不碰 rate 冷却候选 |
| 二次尝试 | 每请求 ≤1 次 | 仅 `SERVER/TRANSPORT/TIMEOUT/EMPTY_RESPONSE`；**429/CHANNEL_BUSY 不重试** |

## 五、为什么成功率不是 100%（结构性，已由 Lead 签字确认）

修好时钟后暴露的真实约束：**「成功率 100%」与「同请求内不重复尝试 + 不排队」在本仿真里互斥**。

- 基线（legacy 复刻）能到 100%：它的 busy-retry **重跑整条链**，同一渠道可被再次尝试，
  第 2 次抽到不同随机结果，于是"兜"住了尾事件；
- 新实现被 v1.3/v1.4 明令禁止重复尝试同一候选（唯一例外 = v1.4 的非 429 瞬时二次尝试，每请求 ≤1 次）、
  也不许排队 ⇒ 当某请求"全部候选都打了一遍且都失败"或"全部候选本地判忙"时只能如实失败；
- v1.4 的二次尝试已把 seed 7 从 95% 拉到 98%（救回 3 个请求）；19991 的 6 个失败属"全候选打尽"，二次尝试救不回（实测 0 个）。

## 六、本轮实现了什么（按契约版本）

1. **v1.1**：`markFailure` 失败率 EWMA（α=0.2；429=1.0、其它=0.6、成功=0）+ `stats/snapshot//state.routing.gate` 暴露 `failRate`；每个失败分支喂样本。
2. **v1.2 / v1.3**：默认策略 `blended` = `loadRatio + failRate` 合成分（纯函数 `candidateScore`，权重写死并可单测）+ 两段有界等待 + last-resort 一次。
3. **v1.4（本次冻结）**：
   - 闸门把 **`busyCoolUntil`（并发满，可被重试放宽）** 与 **`rateCoolUntil`（429 限流，永不放宽）** 分开记账；
   - `adapter`：`RATE_LIMIT → markRateLimited`、并发忙 → `markBusy`；
   - 三处重试（cooldown-retry / 第二段 / last-resort）**只放宽 busy**，并以**显式二次过滤**剔除处于 rate 冷却的候选（防准入"空集兜底"把它们放回）；
   - **二次尝试**：仅非 429 瞬时类、同一候选、每请求 ≤1 次、`countAttempt` 记账、失败同样 `markFailure`；
   - 未改 `ladder.js / failure-map.js / chunks.js / contract.js`（回归红线零改动），零第三方依赖。
